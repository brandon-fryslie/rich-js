On this page

Animation ​

Anything in rich-js that changes with time is an Animation: a value for a time t in seconds, the first moment that value may change, the last moment it may have become what it is, and the same animation with its motion taken out. A step sequence, a sequence of frames, a spinner and an effect are all one, and every other kind of motion is built from the same few pieces, so a host can hold a list of them and ask each the same questions.

typescript
import type { Measurable, Reads, Renderable } from "@promptctl/rich-js";

interface Behavior<T> {
  at(t: number): T;
  validUntil(t: number, moves?: Reads): number;
  validFrom(t: number, moves?: Reads): number;
  reduced(): Animation<T>;
}

// An animation of renderables is a renderable too.
type Animation<T> = Behavior<T> & ([T] extends [Renderable] ? Renderable & Measurable : unknown);
Not run

This is a shape to implement, not a complete program.

Nothing here reads a clock. t is handed in by whoever draws, so the same t gives the same value at one redraw a second or sixty, nothing is kept from one call to the next, and a call costs the same a second in as a million seconds in.

An animation of renderables is itself a renderable, so the way to show one is to put it where a renderable goes (below): in a Panel, a Table cell, a Group, beside static content, and it draws at the time of the frame it is drawn in.

To watch every kind of motion on this page on one timeline — paused, reversed, scrubbed, at a quarter and four times the speed, with motion reduced, at truecolor, 256 colors, sixteen colors and none, at one frame a second and sixty — run npm run animation-playground in a checkout of this repository, or open the playground's demo page.

When it next changes ​

validUntil(t) is never before t, and its answer is one of three things:

  • a later time: the value stays the same until then;
  • Infinity: it never changes again;
  • t itself: it is moving at t, so it changes every frame however close together they are drawn.

An answer may be early — a host then draws a frame that looks like the last one — but never late, since a late answer skips a change. So an animation that cannot say when it holds still answers t.

Some answers are known only once a frame is drawn. An effect on an element holds still where the output cannot show its motion, and only what the element draws says so. So an Effected asked with nothing drawn answers t, and asked about a frame already drawn it is handed what that drawing said, the optional moves argument. Every combinator here forwards it, on the same time it hands the part, so an effect held still at the output holds still in a Timeline.run, a sequence or a repeat too, and the host sleeps. A combinator written by hand that forwards moves to its parts does the same; one that does not stays early, which costs frames and nothing else. A lifecycle is one that does not: a half's schedule also says when the element has arrived or is gone, so it wakes the host until the half ends.

validFrom(t) is the other end of the same validity interval: the last moment, never after t, at which the value may have become at(t) — -Infinity if it always was, t while it moves. Together the two bound the validity interval, [validFrom(t), validUntil(t)), and an answer may be narrower than the truth and never wider. It is what a host running the animation backwards reads: run down the timeline, the value next changes where it began.

Placing one ​

A tween mapped to the text that shows it, an effect over an element, a transition, a lifecycle, a scroll: each is an Animation of renderables, and each is placed as it stands, as the child of any container. It draws its value at the time of the frame it is drawn in, stamps the frame's cells with when it next changes, and under reduced motion draws its reduced form. No t is passed through the program that places it. A print draws for no moment, and an animation printed draws at 0, the start of its own clock. Here a count sits in a panel beside a line that never moves, drawn by a Live whose timeline is sought to one second:

typescript
import { Animation, Console, EASES, Group, Live, Panel, RichText, Timeline, tween } from "@promptctl/rich-js";

const files = Animation.map(tween(0, 1204, { seconds: 2, ease: EASES["ease-out"] }), (n) => new RichText(`${Math.round(n)} files indexed`, { style: "bold" }));
const view = new Panel(new Group(new RichText("indexing the repository"), files), { title: "index", width: 32 });

const recording = new Console({ forceInteractive: false, record: true, width: 40, file: { write: () => {} } });
const live = new Live(view, { console: recording, timeline: Timeline.pause(Timeline.play(0), 0) });
live.start();
live.timeline = Timeline.seek(live.timeline, live.clock.now(), 1);
live.stop();
console.print(recording.exportText());

No container knows that animations exist. A container draws an animation among its children by calling its render with the options it was handed, as it draws any child. Those options carry the frame's time in and carry back out when the animation next changes (onValidity). That works even before it has a cell to draw — a toast not yet entered takes no row — so a container written outside rich-js places one exactly as a Panel does. A program that wants the value instead — its own renderer, a template — reads at(t) and validUntil(t) with no container involved.

The type says which animations can be placed. An Animation<number> is no renderable, and a Panel refuses it at compile time: map it to what shows it first. Animation.all of renderables is a tuple, and is placed by mapping it to a Group, or by placing each one. An animation written as a literal goes through Animation.of, which keeps every member it has and gives it the face that draws it; every combinator below already returns one.

The time a placed animation draws at is always the frame's. That holds inside another animation's value too — the element of a lifecycle, the second part of a sequence, a turn of a repeat: a combinator remaps the time it hands its parts, never what a value contains. Content that should follow a part's clock is composed into the part, with Animation.map or Animation.all, and the result placed. So an animation placed in a repeat's turn does not restart each turn, and Timeline.run over a value does not pause what is placed inside it.

Building one ​

These pieces build every animation, and each says how validUntil and validFrom compose, so an animation built from them answers them without its author doing anything:

  • Animation.constant(value) is value at every time, and never changes.
  • Animation.continuous((t) => value) is the function's value, moving at every moment. Reduced, it holds its first value.
  • Animation.time() is the time itself, in seconds, moving at every moment. It is information, not motion, so reduced it is still the time: map it to a clock or an elapsed counter.
  • Animation.map(animation, f) is the value through f, changing when the source does.
  • Animation.all([a, b, …]) is every one's value at once, in order, changing when the soonest of them does — so several effects drawn as one stay still exactly while each of them does — and having become that when the latest of them did.
  • Animation.sequence(first, seconds, then) is first until seconds, then then, handed the time since it began, so each part runs on its own clock from 0.
  • Animation.repeat(period, nth) is nth(n) through the nth turn of period seconds, handed the time since that turn began: a one-shot played again every period, a different one each turn if nth says so. Turns go on before 0 too, so a timeline run backwards past the start is still in one, and a turn begins on the same moment a step sequence or a WrapMode.loop of the same period does.
  • cyclic(items) is item n of a list for every integer n, counted round it both ways, so -1 is the last: what a rotation through a list is indexed by. Animation.repeat(period, cyclic(turns)) plays the turns in order for ever, and before 0 too. An empty list is refused when the rotation is made.

Each says its reduced form the same way: a constant is itself, a continuous animation holds its value at 0, as a loop holds its first, a mapped one is its source reduced through f, several at once are each reduced, and a sequence or a repeat is each part reduced with its switches kept. A one-shot, such as a tween or a transition, cuts to its end when it starts.

Here a counter moves to a new total every two seconds, each time from the last one, and before 0 it is still counting:

typescript
import { Animation, EASES, cyclic, tween } from "@promptctl/rich-js";

const totals = [0, 120, 870, 430];
const total = cyclic(totals);
const counting = Animation.repeat(2, cyclic(totals.map((to, i) => tween(total(i - 1), to, { seconds: 1, ease: EASES["ease-out"] }))));

for (const t of [0.5, 1.5, 2, 2.5, 4.5, -0.5]) {
  const next = counting.validUntil(t);
  console.print(`t=${t}s  ${Math.round(counting.at(t)).toString().padStart(3)}  next change ${next === t ? "every frame" : `at ${next}s`}`);
}

import { Animation, stepSequence } from "@promptctl/rich-js";

const arriving = Animation.continuous((t) => `arriving ${Math.round(t * 100)}%`);
const blinking = Animation.map(stepSequence([0.5, 0.5]), (i) => (i === 0 ? "on" : "off"));

What is already an animation ​

  • A StepSequence (stepSequence([…]), from the easing vocabulary) is an animation of which step is in progress: at(t) is its index, validFrom(t) when the step began, validUntil(t) when it ends.
  • A FrameSequence is an animation of the frame shown, and a Spinner of the spinner drawn (Frames).
  • An Effect is, for what an element draws in a frame, an animation of what is done to its cells: effect(drawn) is an Animation whose value at t maps each cell's look — its colors and its attributes — to a new one (Effects). A blink is one: blink({ attribute: "bold", off: 0.7, on: 0.3 }) is a step sequence mapped to a frame that sets bold in its second step and leaves every cell as drawn in its first (Effects).

Because a step sequence is an animation, a signal that steps through colors is that step sequence mapped to colors:

typescript
import { Animation, stepSequence } from "@promptctl/rich-js";

const signal = Animation.map(stepSequence([1, 1, 1]), (i) => ["red", "yellow", "green"][i]!);

for (const t of [0, 0.5, 1, 2.9, 3]) {
  console.print(`t=${t}s  [${signal.at(t)}]${signal.at(t)}[/] until ${signal.validUntil(t)}s`);
}

A tween: a value moving to its target ​

tween(from, to, timing) is a number eased from from to to over timing — an ease and its seconds, the pair spring() returns and an effect's Curve carries — and held at to from then on. It is what a progress bar's fill, a counter or a width is handed so it moves to its new value instead of jumping, and it is the first animation here of a value that is never drawn as cells, so its validUntil is its only way of saying when to look again: until 0 before it begins, every frame while it moves, never once it has arrived. It begins at 0 on its own clock; starting it later is Animation.sequence's job, or a timeline's.

A tween lands on its target exactly, whatever the ease, and an ease that overshoots is shown as it is — a count eased by back-out passes its value and comes back. A tween shorter than the gap between a host's frames is simply seen at its end, never mid-way, which is correct at one frame a second and at sixty:

typescript
import { EASES, spring, tween } from "@promptctl/rich-js";

const fill = tween(0, 100, { seconds: 2, ease: EASES["ease-out"] });
const settle = spring({ stiffness: 300, damping: 20 });
const count = tween(0, 50, settle);

for (const t of [0, 0.5, 1, 2, 3]) {
  const next = fill.validUntil(t);
  console.print(`t=${t}s  fill ${fill.at(t).toFixed(1).padStart(5)}%  count ${count.at(t).toFixed(1).padStart(5)}  fill next change ${next === t ? "every frame" : next === Infinity ? "never" : `at ${next}s`}`);
}
console.print(`the spring settles on 50 at ${settle.seconds.toFixed(2)}s: ${count.at(settle.seconds)}`);

A tween keeps nothing from one call to the next, so retargeting it is not a change to it. A tween whose target moves at t₁ is the old tween until t₁, then a new one built from the old one's value there, which is why it starts from where it is and not from its original from:

typescript
import { Animation, EASES, tween } from "@promptctl/rich-js";

const timing = { seconds: 2, ease: EASES.linear };
const first = tween(0, 100, timing);
const retargetedAt = 1;
const fill = Animation.sequence(first, retargetedAt, tween(first.at(retargetedAt), 20, timing));

for (const t of [0.5, 1, 2, 3]) console.print(`t=${t}s  ${fill.at(t)}`);

Over colors, a tween is a ColorRamp read over time: ramp.over(seconds) crosses the ramp's span of positions at a steady rate in seconds and holds at its last stop, each color along the way the ramp's own. A color tween is a two-stop ramp over its seconds, the ramp's ease shaping the move, and a ramp of more stops over time is a sweep through all of them — the blending stays the ramp's, in OKLCH, and nothing here blends a second time:

typescript
import { ColorRamp, ColorRgba, EASES } from "@promptctl/rich-js";

const fade = new ColorRamp(EASES["ease-in-out"], [
  { at: 0, color: new ColorRgba(220, 38, 38) },
  { at: 1, color: new ColorRgba(22, 163, 74) },
]).over(2);

for (const t of [0, 0.5, 1, 1.5, 2]) {
  const hex = fade.at(t).hex;
  console.print(`t=${t}s  [on ${hex}]      [/] ${hex}  next change ${fade.validUntil(t) === t ? "every frame" : "never"}`);
}

A ramp that moves ​

A ColorRamp carries how far it has been moved: scroll, in spans, how far its colors have travelled along it from the first stop to the last, and hue, in turns, how far every color is rotated round the OKLCH hue circle at its own lightness and chroma. Both are constructor arguments after the stops, and both default to 0. A scrolled ramp reads, inside its span, the color that far behind, wrapped round as a repeating gradient. It has no seam when its first and last stops are one color. Outside its span its end colors hold. Unmoved, every read is the ramp's own, stop colors byte for byte.

ramp.moving({ scroll, hue }) is that ramp as an Animation<ColorRamp>: at each t, moved by both parts at t, on top of however far it was already moved. Each part is an Animation<number>, or 0 when not given. Both are fractions, so a phase plugs straight in. Animation.continuous(WrapMode.loop(4)) scrolls the whole span every four seconds, and a tween to a quarter turn rotates the hues and settles. When the moving ramp next changes is the combinators' answer: every frame while a loop runs, and never again once every part has settled.

typescript
import { Animation, ColorRamp, ColorRgba, EASES, WrapMode, tween } from "@promptctl/rich-js";

const hues = new ColorRamp(EASES.linear, [
  { at: 0, color: new ColorRgba(255, 120, 100) },
  { at: 0.5, color: new ColorRgba(110, 190, 255) },
  { at: 1, color: new ColorRgba(255, 120, 100) },
]);
const moving = hues.moving({ scroll: Animation.continuous(WrapMode.loop(4)), hue: tween(0, 0.25, { seconds: 2, ease: EASES["ease-out"] }) });

for (const t of [0, 1, 2, 3]) {
  const ramp = moving.at(t);
  const swatches = [0, 0.25, 0.5, 0.75].map((v) => `[on ${ramp.at(v).hex}]    [/]`).join("");
  console.print(`t=${t}s  ${swatches}  scroll ${ramp.scroll.toFixed(2)}  hue ${ramp.hue.toFixed(2)}  next change ${moving.validUntil(t) === t ? "every frame" : "never"}`);
}

Anything that reads a ramp reads a moved one, since it is still a ColorRamp. Laid across what an element draws, it is the gradient effect: a rule's line or a panel's border that flows and turns. A gradient holds still on a sixteen-color terminal, where a move would be a jump between slots. That is decided where the gradient is drawn, from the depth the output is written at.

A glyph effect: text typed, scrambled and rained on ​

An effect moves the colors of what an element draws. A GlyphEffect changes the glyphs instead, and it has the same shape. Handed every cell the element draws in a frame, it gives an Animation whose value at t maps each cell to the text it shows. Color and glyph are not two kinds of animation: both are a per-cell map that changes with time. GlyphEffected is any renderable under a glyph effect over time, an animation placed like any other; its value at t, .at(t), is the element through the effect at that moment:

typescript
import { EASES, GlyphEffected, RichText, typewriter } from "@promptctl/rich-js";

const typing = typewriter({ seconds: 2, ease: EASES.linear });
const line = new RichText("typed one cell at a time");

for (const t of [0, 0.5, 1, 1.5, 2]) {
  console.print(new GlyphEffected(line, typing.effect, { key: "line" }).at(t));
}
console.print(`done at 2s: ${typing.done(2)}`);

A glyph effect changes what a cell shows, never which cells exist, where they are or who drew them. The text it returns for a cell must be exactly as wide as the glyph it replaces, hold no line break or control character, and not join the cell beside it into one character, as a trailing zero-width joiner would. Otherwise the render throws and names the cell or the line. So nothing beside the element ever moves, and a wide glyph like 漢 is blanked as two spaces or scrambled as two narrow glyphs, never cut in half. A cell that comes back unchanged is drawn byte for byte as it was, and a changed cell keeps its link and its owner. Glyphs are written at every color depth, so a glyph effect moves even with no color output, where a color effect does nothing.

The catalogue, GLYPH_EFFECT_CATALOGUE, has four transitions, which run once and say when they are done — two that bring text in and their two ways out, for an element leaving — and three loops:

  • typewriter(timing): the element's text blank until it is typed, in reading order, the last cell at timing.seconds, its ease setting the pace. The spaces between words are typed; the padding round the text is not, so no time is spent on it.
  • scramble(timing, z): random glyphs, a new one each fifteenth of a second, resolving to the words in reading order. Blanks stay blank, so the words keep their shape.
  • backspace(timing) and scrambleOut(timing, z): the two ways out — the text erased from its last cell to its first, or each cell churning in reading order before it blanks — whole at 0 and blank at timing.seconds.
  • caseWave({ step, width }, z): a band of swapped case crossing the element one column a step.
  • particles(spec, z): particles on the element's blank cells, never over its words. rain falls a row a step, and stars are drawn afresh each life. Both are values of the one particles function, and their specs are in GLYPH_DEFAULTS. Each spec names an ASCII set too, which is drawn instead on an output that draws ASCII alone.

marchingAnts({ step, every }) is a loop that goes round a box rather than through text: gaps in the frame at most every cells apart, spaced as evenly as the ring allows, walking one cell clockwise a step. Its defaults are GLYPH_DEFAULTS.march:

typescript
import { GLYPH_DEFAULTS, GlyphEffected, Panel, marchingAnts } from "@promptctl/rich-js";

const marching = new GlyphEffected(new Panel("the ants march round", { title: "border" }), marchingAnts(GLYPH_DEFAULTS.march), { key: "border" });

console.print(marching.at(0));
console.print(marching.at(0.15));

It marches whatever box the element draws, at any width, past a title, and each box of several. A frame is told by what drew it, not by its glyphs, so a line in the element's content that looks like a border stays still. Panel and Table say which cells are their frame. The ring is the frame's outer edge, and the rules inside it stay still, so an element with no ink on that edge, such as a Table with showEdge: false, one too narrow for its edges, or one of SIMPLE whose only ink is its head rule, is left as written and never changes. The ring is the box as the element draws it, so wrap the box itself and not a Viewport cropping it.

A transition moves every frame until it is done, then never. A loop moves in steps, because a cell shows one glyph or another, and its validUntil is when its next step begins. A glyph effect and a color effect compose by nesting: the outer wrapper is drawn over what the inner one drew, so here a wave of capitals crosses a line that is turning red:

A transition from one renderable to another ​

A fade-in or a dissolve is one element arriving or leaving. When the same slot changes from one renderable to another — a status going from "building" to "done", a number becoming a different number — crossfade(curve) and wipe(curve) draw the change instead of a cut. Each is a Transition like the others, so it says when it is done, and its value is a Change: handed the renderable drawn until now, the one drawn from now on and the terminal they are drawn on, it gives an Animation of what to draw, from t = 0 on its own clock.

Every cell goes through the terminal's ground on its way. Until it is halfway it shows the old renderable, fading out, and from then the new one, fading in, so no cell jumps from one glyph to another. A crossfade turns every cell together. A wipe sends a front across the columns from left to right, with the new renderable behind it and a soft edge six columns wide, or as many as its second argument says.

The change is drawn at the new renderable's size from its first frame. The old one is cut or padded to the new one's rows, so what sits beside it moves once, at the cut, and never while the change runs. It moves every frame until it is done, then it is the new renderable itself, byte for byte, and never changes again. A change shorter than the gap between frames is seen at its end:

typescript
import { EASES, RichText, wipe } from "@promptctl/rich-js";

const change = wipe({ seconds: 2, ease: EASES.linear, swing: 1 });
const moving = change.effect({
  from: new RichText("building the project", { style: "yellow" }),
  to: new RichText("done: 1,204 tests passed", { style: "green" }),
});

for (const t of [0, 0.5, 1, 1.5, 2]) {
  console.print(moving.at(t));
}
console.print(`done at 2s: ${change.done(2)}, next change ${moving.validUntil(2)}`);

Enter and exit: an element arriving, staying and leaving ​

A row added to a table, a line appended to a log, a panel closing: each is one element that arrives, stays, and leaves, and whoever holds it must know when it is gone so it can drop it. lifecycle(element, { enter, exit, key }, entered) is that element on the host's clock, as an Animation of what it draws. enter and exit are its two halves, each a Half: handed the element and its key, it gives an Animation of the element as the half draws it, from t = 0 on the half's own clock, in the shape a Change has. The half is done from the first moment its animation says it never changes again (Animation.done): an arrival is the element from then, and an exit is gone. throughColors(transition) makes one from a color transition, arriving from and leaving to the ground of the terminal the frame is drawn on, and throughGlyphs(transition) from a glyph one, which is written with no color output too; each lends the transition's schedule to the frames, which is the one word on when they change that an Effected on its own lacks until it is drawn, so an Effected or GlyphEffected handed in bare is refused when the lifecycle is made: a half must end. An arrival starts from nothing — fadeIn, typewriter, scramble — and an exit ends at nothing — dissolveOut, backspace, scrambleOut — so the element is already out of sight when it is dropped. The two kinds mix, so a line can type itself in and dissolve out, and a half written by hand is any function of that shape: (element) => Animation.sequence(Animation.continuous((t) => new Padding(element, [0, 0, 0, Math.round(8 * (1 - t))])), 1, Animation.constant(element)) slides the element in from the right, which no effect draws. key names the element for both halves' seeds. entered is the host time it arrived. lifecycle.leave(at) is the same element told to leave at host time at, a new value like a timeline operation's. Until it is told, its left is Infinity.

Both times are handed in, never read, so a host that says "leave at 5" and asks for the frame at 6 gets the element one second into leaving. At host time t it draws:

  • before entered, nothing — a timeline run backwards asks for those times;
  • arriving, the element through enter, handed the time since it entered;
  • staying, the element itself, byte for byte, until it is told to leave;
  • leaving, through exit, handed the time since it was told, over whatever arriving would draw then, so an element told to leave before it has arrived leaves from where it is — though a color exit is spread over the cells each frame shows, so a cell the arrival adds can move one already leaving back toward whole;
  • once exit is done, nothing, for good: gone(t) is true, and the host drops it.

While it arrives or leaves it changes when its half does — every frame for a fade, once a step for one sampled on a step sequence (sampleAndHold(fadeIn(curve, 0), stepSequence([0.25])) arrives a quarter of a second at a time, and a host wakes on those quarters) — and it holds still while it stays and once it is gone, so a host still holding a gone element wakes for nothing. A half says when its frame changes whatever the element draws, so this holds even with no color output, where a color half writes nothing. Placed, the lifecycle stamps its frame with that validity interval:

typescript
import { EASES, RichText, dissolveOut, lifecycle, throughColors, throughGlyphs, typewriter } from "@promptctl/rich-js";

const typing = { seconds: 1, ease: EASES.linear };
const line = new RichText("compiling 214 modules", { style: "bold cyan" });
const halves = { enter: throughGlyphs(typewriter(typing)), exit: throughColors(dissolveOut({ ...typing, swing: 1 }, 0)), key: "line" };
const shown = lifecycle(line, halves, 0).leave(3);

for (const t of [0, 0.5, 1, 2, 3.5, 4]) {
  const next = shown.validUntil(t);
  console.print(shown.at(t));
  console.print(`t=${t}s  gone ${shown.gone(t)}  next change ${next === t ? "every frame" : next === Infinity ? "never" : `at ${next}s`}`);
}

Scroll, marquee and slide ​

A long line panning across a fixed width, a log tail stepping down, a panel sliding into place: each is a window over content wider or taller than its slot, with the content's offset in the slot moving with time. scroll(content, { width, height, col, row }) is that window as an Animation of what it draws. col is how many cells of the content sit left of the slot, and row how many rows sit above it. Each is an Animation<number>, 0 when not given, and is rounded to the nearest cell. A scroll and a slide are the same window with a different offset handed in: a step sequence, or a tween to 0.

marquee(content, { width, step }) is that window crossing its content: the content moves one cell left every step seconds, leaves on the left, and comes in again from the right, for ever and before 0 too. Its span is the content's natural width plus the slot's, read when the frame is drawn, so any renderable with a natural width crosses, not only a line of text. The slot is as tall as the content, so every row of it crosses. It changes only on a step's boundary, whatever the content's width, so the host sleeps between steps. Reduced, it holds at step 0, the content's start in view.

The window is its slot. It measures as its width and draws exactly its rows of its width at every offset, cropped only to a narrower room it is given, so nothing beside it moves. An offset before or past the content shows blank cells instead of stopping at an edge, which is how a marquee enters from the right and a slide-in arrives from outside the slot. The content is drawn at its own natural width and length. Content that should wrap to the slot instead goes in a Constrain of the slot's width, and so does content with no natural width of its own, such as a Rule, which fills whatever it is given; the scroll refuses that content by name rather than draw it at an unbounded width. An offset that is not a finite number is refused the same way. A wide glyph cut by an edge is blanked, never halved, and each cell keeps its anchor in the content, so hit-testing finds its owner through a moving window. When it next changes is when either offset does: on each step of a stepped scroll, and never once a slide-in has arrived. A frame it draws also carries the soonest change of anything in its content, shown or not, because an element entering above the slot moves every row in it.

typescript
import { EASES, RichText, marquee, scroll, tween } from "@promptctl/rich-js";

const news = marquee(new RichText("every motion is one Animation ·", { style: "bold yellow" }), { width: 16, step: 0.125 });
const slide = scroll(new RichText("arrived", { style: "green" }), { width: 16, height: 1, col: tween(-16, 0, { seconds: 1, ease: EASES["ease-out"] }) });

for (const t of [0, 0.5, 1, 2, 3]) {
  console.print(news.at(t));
  console.print(slide.at(t));
  console.print(`t=${t}s  marquee next change at ${news.validUntil(t)}s, slide next change ${slide.validUntil(t) === t ? "every frame" : "never"}`);
}

Playback: a timeline ​

Because every animation is a pure function of its time, pausing, reversing, scrubbing and speeding one up are not things done to the animation: they are a change in which time it is asked for. A Timeline is that map from the host's clock to animation time, as a value — an animation time at a host time and a rate in animation seconds per host second, or, paused, one animation time at every host time. Every operation takes a timeline and a host time and gives a timeline back, so a paused timeline resumed later maps the moment it resumes to the time it froze at, and nothing here reads a clock.

  • Timeline.play(origin, rate = 1) plays from host time origin, at which the animation is at 0; a negative rate runs it backwards.
  • Timeline.pause(timeline, host) holds it at the animation time it maps host to; Timeline.resume(timeline, host) plays on from there.
  • Timeline.seek(timeline, host, time) puts the animation at time at host time host, playing or held as it was.
  • Timeline.withRate(timeline, host, rate) changes the rate from host on, with no jump.
  • Timeline.at(timeline, host) is the animation time at a host time.
  • Timeline.stagger(animations, delay) runs each animation on a timeline offset by its index times delay (below).

Timeline.run(timeline, animation) is the animation on host time: its value at the mapped time, and its validUntil carried back onto the host's clock — forwards, the host moment the mapped time reaches the animation's own answer; backwards, the moment it drops under where the value began, which is what validFrom is for; paused, never. A host reads the answer in its own seconds whatever the rate:

typescript
import { Animation, Timeline, stepSequence } from "@promptctl/rich-js";

const signal = Animation.map(stepSequence([1, 1, 1]), (i) => ["red", "yellow", "green"][i]!);
const say = (label: string, timeline: Timeline, host: number) => {
  const played = Timeline.run(timeline, signal);
  const next = played.validUntil(host);
  console.print(`${label.padEnd(22)} host ${host}s → ${Timeline.at(timeline, host)}s  [${played.at(host)}]${played.at(host)}[/]  next change ${next === Infinity ? "never" : `at host ${next}s`}`);
};

const playing = Timeline.play(10);
say("playing from 10", playing, 11.5);
say("at half speed", Timeline.withRate(playing, 11.5, 0.5), 12);
say("backwards", Timeline.withRate(playing, 11.5, -1), 12);
const paused = Timeline.pause(playing, 11.5);
say("paused at 11.5", paused, 100);
say("resumed at 100", Timeline.resume(paused, 100), 101);
say("sought to 2.5", Timeline.seek(playing, 11.5, 2.5), 11.5);

A stagger: one animation across children ​

Most motion looks right in cascade: a group's children pulsing in sequence, a light walking down a list. Timeline.stagger(animations, delay) is every one of animations at once, each on a timeline playing from its index times delay seconds after the earliest, their values in order. It is Animation.all of Timeline.runs, so it changes when the soonest child does, with each child's answer carried onto the stagger's clock, and it holds still in a gap between one child settling and the next one starting. The stagger runs on its own clock from 0, and its earliest child starts there: a delay of 0 starts them together, and a negative one starts the last child at 0 and the first last.

Before its turn, a child is asked for a time before 0. What that shows is the child's own business, and a loop is shifted in phase, which is what a staggered pulse is. Playing, pausing or reversing the whole group is one more timeline run over it.

A lifecycle is staggered by its own entered instead: rows arriving one after another are Animation.all of lifecycles entered at each row's index times the delay. Its leave and gone take the host's clock, so it has to stay on that clock, not move onto one shifted by its index. A row that has not arrived yet, or is gone, draws nothing, and a Tree ends its branch at the last child that does draw.

No container knows that a stagger exists. A Group, a Table's rows, a Tree's children and a Layout's panes take the children's frames the way they take any renderables, through Animation.map, and placed — as a Live's view, or in a Panel — the frame says when it changes as the stagger does. Here the stagger is read as a value instead: log.at(t) at each moment, and log.validUntil(t), the moment that frame would say:

typescript
import { Animation, Group, RichText, Timeline, stepSequence } from "@promptctl/rich-js";

const steps = ["resolving dependencies", "compiling 214 modules", "bundling the browser build"];
// Lit for half a second, dim for a second, looping: half a second apart, the light walks down the list.
const lit = steps.map((step) => Animation.map(stepSequence([0.5, 1]), (index) => new RichText(step, { style: index === 0 ? "bold cyan" : "dim" })));
const log = Animation.map(Timeline.stagger(lit, 0.5), (frames) => new Group(...frames));

for (const t of [0.2, 0.7, 1.2]) {
  const next = log.validUntil(t);
  console.print(log.at(t));
  console.print(`t=${t}s  next change at ${next}s`);
}

Playing in a Live or an App ​

A Live and an App each hold a timeline, playing from 0 when the host is made, at the clock's pace, unless the timeline option gives another. Each frame, the host reads its clock once, draws its view for the time the timeline maps that moment to — every animation placed anywhere in it draws at that time — and carries what the frame's cells say about when it changes back onto the clock through Timeline.run. So pausing, reversing, scrubbing and speeding up what a host shows means replacing host.timeline, and host.clock is where the host time those operations take is read. Replacing it draws one frame for the new time. A paused timeline then holds that frame: an App waits on nothing until the timeline plays again, though refresh() still draws. Any view may also read state the host cannot see, such as a table mutated in place, so a Live still polls it at its rate, each frame drawn at the held time. A renderable that keeps time between frames, such as a Progress, reads it from its host, so it is on the timeline wherever it sits in the view (see below).

The view can be an animation placed as it stands, or a container holding one. That is how a value that is never drawn as cells tells the host when to look again: a tween mapped to the bar that shows it moves every frame until it arrives, then never again, and the host draws exactly that long. A sequence that holds still wakes the host once, at its switch. Here a Live on a paused timeline is sought to a moment and drawn there. Its console is not interactive, so it writes the frame once, at stop(), and the recording is printed below:

typescript
import { Animation, Console, EASES, Live, RichText, Timeline, tween } from "@promptctl/rich-js";

const width = tween(0, 20, { ease: EASES.linear, seconds: 2 });
const bar = Animation.map(width, (w) => new RichText(`${"█".repeat(Math.round(w)).padEnd(20, "·")} ${w.toFixed(1)}`));

const recording = new Console({ forceInteractive: false, record: true, width: 40, file: { write: () => {} } });
const live = new Live(bar, { console: recording, timeline: Timeline.pause(Timeline.play(0), 0) });
live.start();
live.timeline = Timeline.seek(live.timeline, live.clock.now(), 1.5);
live.stop();
console.print(recording.exportText());

Reduced motion ​

Terminals have no prefers-reduced-motion, so the program hands the reader's preference in, once: reducedMotion: true on a Console, which a Live draws through, or on an App, and on the frame the template functions are handed, which a template drawn in a rich-js frame takes from that frame. Nothing reads it from the environment; a program that wants an environment variable to decide reads it itself.

Under it every animation is drawn as its reduced() form: what it shows, and when it starts and stops showing it, are kept, and every moment of motion between is skipped. A loop holds its value at 0, so a loop that should rest on something starts there; a glyph loop draws the text as written. A one-shot cuts from its start to its end the moment it starts (Animation.cut(before, after)), a transition to its new state, a stagger has every child arrived, and an element is there from when it entered until it is told to leave, with no fade either way. A timeline still maps the time, so what shows follows it. A host wakes only when content changes: never for a spinner or a fade, once each for an element arriving and leaving. Text styled blink or rapidBlink is written without it, because the terminal would blink it on its own. That holds for every output the preference reaches: a print, a Live or App frame, renderToString, and a recording console's exports. Segments encoded by hand — a template's, say — are written for the OutputTarget they are given, so hand it the same preference: resolveOutputTarget("auto", { reducedMotion: true }).

Every animation placed in a view is drawn reduced where it is drawn. Animation.continuous says its value is motion, so reduced it holds still. The time itself is not motion: a clock, an elapsed counter or a log of what has happened by now is mapped from Animation.time(), which reduced is still the time, so it stays on time while every animation placed in what it maps to is reduced where it is drawn. What a program samples itself with at(t) is its own and still moves; to have it reduced, place the animation instead, mapped to what shows it.

Here the same spinner and typewriter are drawn at three moments, with motion and reduced, each by a Live whose timeline is held there:

const view = new Group(new Spinner("dots", "building"), new GlyphEffected(new RichText("hello, world"), typing.effect, { key: "greeting" }));
const at = (reducedMotion: boolean, t: number): string => {
  const drawn = new Console({ reducedMotion, forceInteractive: false, record: true, width: 30, colorSystem: null, file: { write: () => {} } });
  const live = new Live(view, { console: drawn, timeline: Timeline.seek(Timeline.pause(Timeline.play(0), 0), 0, t) });

  live.stop();

How a host knows when to draw again ​

Whoever draws an animation's value as cells at a time stamps every cell it draws with the validity interval the animation is in there: validUntil and validFrom, on the cell's Style. The stamp rides up through any container as an anchor does and writes no byte, and whoever holds the composed frame reads the soonest change with Segment.validUntil and the latest start with Segment.validFrom, which a host running its timeline backwards needs. A stamp laid over one a value's cells already carry keeps the sooner change and the later start, so a frame's validity interval is the intersection of its cells': narrower than the truth, never wider. A placed animation also tells its validity interval to the onValidity of the render options it was drawn under, which reach it wherever the frame's time does, so an element not yet entered, which draws no cell, still says when it will, and a switch cropped out of view still wakes the host, since it may move the rows in view. The frames of an Effected element are left out of what it tells: they ride only on its cells, so a Viewport scrolled past them stops waking the host for them. Anything that switches — a lifecycle's arrival or exit, a caret's blink — still tells, wherever it is cropped, and so does everything in a scroll's slot (above). A host intersects what it is told with what the cells say. An effect's frame tells the validity interval it drew in to onReads, with its key and the time it was drawn at, since that may not be the frame's: whatever placed the animation carries it back through the combinators that remapped the time (moves, above). That is how a Live knows when to wake without asking each piece of its view what it holds.

Every placed animation stamps, choosing its frame where it is drawn, so under reduced motion it draws its animation reduced and stamps only where content changes. An Effected, a GlyphEffected and a Spinner stamp exactly: each knows when it next changes only once it has the output's depth, terminal and asciiOnly, so a loop that holds still at the output's depth says it never changes there, and the host sleeps. So does the template frames function, whose frame is spliced into a line at the time it is handed. Nothing an animation's at returns carries a stamp of its own — not a scroll's frame, a change's, a lifecycle's or a spinner's — because the time it is asked for may be one a timeline, a sequence or a lifecycle mapped from the frame's: the placed animation stamps its own answers at the frame's time, which every one of those maps carries back, so a change under a paused timeline says it never changes, and a lifecycle arriving on a step sequence wakes its host on each step.

A renderable that lives from one frame to the next, such as a widget, is not rebuilt for each frame. It reads the time instead from its render options: frame.time is the moment the frame is drawn for, on the clock its stamps are read on, and frame.host is the identity of the host drawing it, with nothing on it to read. A frame has one time: a renderable drawing in it cannot ask the host for a second, and a host asked for its frame inside a render throws. That is the timeline's time, for every view, so its stamps are on the clock the host reads them on, and pausing holds it. Between frames a host hands the frame it would draw now to whoever asks, host.frameNow(), and a print is drawn in the frame its caller names, console.print(progress, { frame: progress.frameNow() }); a print that names none is drawn for no moment, 0, and nothing drawn from it moves. A TextInput's blinking cursor is one. Every event a WidgetApp hands a widget — a key, a click, a change of focus — carries the time of the frame the app would draw then as its time, so the field restarts its blink there without reading a clock. A Progress is another: what it hears between frames is an update from the program, so it is made for one host and stamps each update with the time of that host's frameNow(), and a frame from any other host makes it throw, since its stamps would be on another clock — as does a print that names no frame, since 0 is a moment before every task began.

An animation of a value that is never drawn as cells — a number, a color — has no cell to carry a stamp, so its validUntil is the only way it says when to look again.
